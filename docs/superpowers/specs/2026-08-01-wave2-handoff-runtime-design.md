# wave2 引き継ぎ実行時挙動の設計

## 背景

Issue #2 の波2では、SessionStart フックが利用者の置いた `pending/` の内容を読む境界と、読み取り後に `consumed/` へ移す実行時処理を強化する。対象は `scripts/handoff-check.sh`、`scripts/handoff-consume.sh`、`scripts/lib/common.sh`、対応する2つのテスト、`skills/session-handoff/SKILL.md` に限定する。

## 目的と非目的

目的は次の4点である。

1. ハードリンク、置き場外リンク、リンク切れ、FIFOなどを本文として注入しない。
2. 異常項目・消費失敗項目の報告量を制限し、攻撃者が決めたファイル名によるstdoutの膨張を防ぐ。
3. stdout切断、SIGTERM、消費競合が起きても、本文を「移動済みだが未配送」の状態で失わない。
4. 手動一括消費が1件の失敗で後続ファイルを放棄しない。

対象外は、install/uninstallの利用者ファイル保護、テストランナーの検出力、README全体の記述整合、CIジョブの追加である。これらはIssue #2の後続波で扱う。

## 採用案

既存のBash実装を維持し、共通移動処理に原子的な宛先予約を追加する。Python化や新しい常駐プロセスは採用しない。

### ファイル分類

`handoff-check.sh` は `find -L` の結果を次のように分類する。

- 通常ファイルでリンク数が1のものだけを本文候補にする。
- 通常ファイルだがリンク数が2以上のものはハードリンクとして異常項目にする。
- リンク切れ、置き場外を指すリンク、ディレクトリを指すリンク、FIFOなどは本文を読まず異常項目にする。
- 実ディレクトリは既存仕様どおり下書き置き場として無視する。

異常項目は本文を読まず、移動できるものだけを `consumed/` へ移す。報告は異常カテゴリ全体で最大10件とし、超過分は件数だけを固定文で知らせる。消費失敗も最大10件を報告し、超過分は件数だけを知らせる。ファイル名・パスはこれまでどおり区切りタグの属性だけに置き、区切り外の固定文へ埋め込まない。

### claim / output / commit

通常ファイルと異常項目は、処理プロセス固有の `pending/.inflight.<pid>/` へ `mv` してclaimする。claim後のファイルについて、本文と警告を一時spoolへ完全に生成する。spoolをstdoutへ `cat` し、catが成功した場合だけ予約済みの `consumed/` 宛先へcommitする。

stdoutへの書き込みが失敗した場合、またはHUP/INT/TERM/PIPEを受けた場合は、予約を解放してinflightのファイルをpendingへ戻す。commit済みの項目は復元対象から外す。spoolと空のinflightディレクトリは最後に片付ける。これにより、`| head -1` のような読み手の終了で本文だけが消費済みになることを防ぐ。

宛先名は `dest` の存在確認だけに依存しない。`dest.cts-lock` を `mkdir` で先に予約し、競合したプロセスは次の `.dupN` 候補へ進む。予約後に宛先の存在（壊れたシンボリックリンクを含む）を再確認してから移動する。

### 上限と発火源

通常ファイルは従来どおり1件8,192バイト、合計32,768バイト、最大5件とする。次のファイルを加えると合計を超える場合は、そのファイル以降をpendingに残す。claimに失敗したファイルはスロットとバイトを消費せず、後続のファイルを試す。発火源は `startup` と `clear` のみとし、`resume` は会話履歴を復元するため自分自身の引き継ぎを消費しない。

一括の `handoff-consume.sh` は全候補を順に試し、失敗をstderrへ記録しながら最後まで処理し、最後にまとめて非0を返す。

## テスト方針

実装前に次の回帰テストを追加し、現行実装で失敗することを確認する。

- ハードリンク、ディレクトリシンボリックリンク、FIFOが本文へ出ず、異常として退避される。
- 11件以上の異常項目と消費失敗を作っても、報告件数とstdoutバイト数に上限がある。
- 先頭候補のclaim失敗後に後続の通常ファイルが配送される。
- 合計上限を超える5件目を消費せず、4件までを配送する。
- `source=resume` ではpendingを消費しない。
- `handoff-check.sh | head -1` 後もpendingに本文が残り、再実行で配送できる。
- `handoff-consume.sh` の一括処理が先頭の失敗後も後続を消費する。
- 同名宛先への並行移動で既存内容を上書きしない。

既存の全テスト、bash構文検査、レビュー対象差分の空白検査を実装後に実行する。

## 代替案と判断

Pythonヘルパーへ移す案は、ファイルclaimとシグナル処理を明確に書ける一方、SessionStartの依存環境を増やし、既存Bash 3.2互換の検証範囲を広げるため採用しない。

現行の「consumedへ移してからstdoutへ書く」順序を維持する案は変更量が小さいが、stdout切断時の本文消失を解消できないため不採用とする。

この設計はユーザー承認済みであり、wave2の実装計画へ移行する。
