# Issue #16: 個人設定と共有設定の更新経路を分離する設計

## 1. 背景と目的

現在の `install.sh` は、次の2種類のファイルを同じ実行で変更する。

- 個人設定: `.claude/settings.local.json`（フック登録先。通常は版管理外）
- 共有設定: `.gitignore`（リポジトリへコミットされ得る共有ファイル）

この組み合わせは後方互換性のある既定動作として維持する。一方で、共有リポジトリへ
導入する開発者が `.gitignore` だけを更新したい場合や、個人環境だけへ導入して共有ファイルを
触りたくない場合に、意図をCLIで明示できるようにする。

## 2. 用語とCLI方針

操作対象のスコープを次の3つに分ける。

| スコープ | 指定 | `install.sh` | `uninstall.sh` |
| --- | --- | --- | --- |
| 全体（既定） | 引数なし | 個人設定と共有設定の両方 | 個人設定と共有設定の両方 |
| 個人 | `--personal` | 個人用の状態・スキル・フック・台帳だけ | 個人用の設置物だけ。`.gitignore`は残す |
| 共有 | `--shared` | `.gitignore`だけ | `.gitignore`だけ。個人用の設置物は変更しない |

`--personal` と `--shared` は同時指定を拒否する。引数なしの動作は変更せず、既存利用者の
再実行や既存の自動化を壊さない。`uninstall.sh` の既存オプション `--guess` は個人側の
推測取り外しにだけ適用する。`--shared --guess` は意味が曖昧なので拒否する。

不明なオプション、複数の導入先ディレクトリ、スコープの重複は、変更を始める前にエラーと
する。ヘルプには各スコープの変更範囲と、引数なしが従来どおり全体動作であることを表示する。

## 3. installの動作

### 3.1 全体（既定）

既存の処理順序と責務をそのまま維持する。

1. `.token-saver/` の状態ディレクトリと導入先 token-report entrypoint を用意する
2. `settings.local.json` のバックアップ、フック登録、台帳更新を行う
3. スキルをリンクまたはコピーで配置し、台帳へ記録する
4. 台帳上で実際に設置したスキルだけを含めて `.gitignore` ブロックを再生成する

### 3.2 `--personal`

全体動作のうち個人側の処理だけを行う。

- `.token-saver/handoff/`、token-report entrypoint、`settings.local.json`、スキル、台帳を
  既存の安全規則に従って処理する
- `.gitignore` を読まず、作成・更新・台帳フラグの記録を行わない
- `.gitignore` を変更しないため、導入した絶対パスのスキルリンクなどが未追跡として見える
  可能性を出力で案内し、共有側を更新するには `--shared` を再実行するよう伝える

個人側の処理が途中で失敗した場合は、既存どおり適用済み項目と `uninstall.sh` による復旧手順を
表示する。`.gitignore`を後から推測で変更してはならない。

### 3.3 `--shared`

`.gitignore` ブロックだけを更新する。

- `.token-saver/` は常にブロックへ含める
- 現在の台帳に記録されたスキルがあれば、そのスキルの相対リンク行だけを含める
- 新パスの台帳が無く旧パスの台帳だけがある場合は、旧台帳を読み取り専用で参照する
- 台帳が無い場合はスキルを推測せず、`.token-saver/` だけを含める
- `settings.local.json`、フック、スキル、状態ディレクトリ、台帳、バックアップは作成・更新・
  移行しない

台帳に無いスキルを推測して `.gitignore` へ追加しない。これは、導入先が自前で持つ同名スキルや
複数クローンのリンクを、意図せず版管理から隠すことを防ぐためである。`.gitignore` が存在しない
場合は共有モードの明示的な要求として作成してよいが、共有モード自身の所有記録を台帳へ作らない。

## 4. uninstallの動作

### 4.1 全体（既定）

既存どおり個人用の設置物を外した後、取り残しが無ければ `.gitignore` ブロックも外す。台帳の
fail-closed、`--guess`、引き継ぎ本文の保持、利用者の差し替え検出は維持する。

### 4.2 `--personal`

個人用のフック、スキル、token-report entrypoint、状態、バックアップ、台帳だけを既存規則で
取り外す。`.gitignore` は一切変更しない。

個人用の設置物を取り残した場合は、既存どおり台帳を残して警告する。個人側を外し切っても、
共有設定の取り外しは利用者が明示的に `--shared` で行う。

### 4.3 `--shared`

`.gitignore` ブロックだけを取り外す。個人用の設定・フック・スキル・状態・台帳は変更しない。

ただし、管理対象のスキル、token-report entrypoint、handoff/state の実ファイルが残っている
場合は、それらを消さずに警告し、`.gitignore` ブロックも残す。除外だけを先に外して絶対パスの
リンクや作業記録を未追跡として露出させないためである。共有モードだけで作成した空の
`.gitignore` を、所有記録が無い状態で削除してはならない。

台帳が無い場合も、導入先のファイル名やリンク先から個人用設置物を推測して削除しない。
既存の fail-closed と `--guess` の安全境界を保つ。

## 5. 実装境界と安全性

- `install.sh` / `uninstall.sh` の引数解析でスコープを決定し、各処理段階を条件付きで実行する
- `.gitignore` の編集は既存の `lib/gitignore-block.py` と原子的書き込みを使う
- `--shared` では settings の writable check、設定バックアップ、管理ディレクトリ作成、台帳更新を
  実行しない
- `--personal` では `.gitignore` の writable check、読み込み、更新を実行しない
- シンボリックリンク、権限、混在改行、利用者の既存ブロック、未追跡ファイルを既存の保護規則で
  扱う
- 台帳の行プロトコルや既存のパス、フックの matcher、token-report 集計ロジックは変更しない
- モードをまたいだ再実行は冪等にする。各モードが自分の対象外のファイルを変更しないことを
  差分・mtime・内容で検証する

## 6. テスト方針

既存の全体テストを維持し、`test/test-install.sh` と `test/test-uninstall.sh` に次を追加する。

- 引数なしが従来どおり個人・共有の両方を更新する
- `install.sh --personal` が settings・スキル・状態を更新し、`.gitignore` の内容とmtimeを変えない
- `install.sh --shared` が `.gitignore` だけを更新し、settings・スキル・状態・台帳を作らない
- 既存台帳がある共有モードは、実際に記録されたスキルだけをブロックへ含める
- 台帳が無い共有モードはスキルを推測しない
- `uninstall.sh --personal` が個人用設置物を外して `.gitignore` を残す
- `uninstall.sh --shared` が個人用設置物を残し、スキル・entrypoint・handoff/state が残る場合は
  `.gitignore` も残す
- shared先行、personal先行、再実行、複数クローン相当のパス変更を安全に扱う
- 既存の権限、シンボリックリンク、利用者のブロック、未追跡ファイルを壊さない
- 不正なスコープ指定をファイル変更前に拒否する

全体テスト、Bash 3.2 E2E、構文検査、`git diff --check` を通過させる。

## 7. 非対象

- SessionStart matcher の仕様変更
- handoff本文の区切りタグ安全性の再評価（Issue #15）
- Python 3.6 / 3.8 の実機検証（Issue #17）
- token-report の集計ロジック
- `.claude/settings.json` など別の設定ファイルへの対応
