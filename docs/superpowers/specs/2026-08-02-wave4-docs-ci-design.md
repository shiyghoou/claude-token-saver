# 波4: 記述と実態の整合、およびCIの検査漏れを解消する

- Issue: #11
- 親Issue: #2
- 状態: 採用

## 背景

波3までで、テストランナー自身の検出力と既存機能の回帰テストが整備された。一方で、READMEやシェルスクリプトのコメントには、実装が保証する範囲より強い表現や、実行環境と一致しない説明が残っている。また、GitHub Actionsではテストランナーのスキップ防止、全シェルスクリプトの構文検査、ShellCheckが常時実行されていない。

波4では、実装の挙動を変えずに、説明を実測へ合わせ、CIの検査経路を明示的に追加する。

## 目標

1. READMEと対象コメントが、現行実装の保証範囲・制約・実行環境を正確に説明する。
2. CIが、テストのスキップを成功扱いにせず、Git管理下のシェルスクリプトを構文・静的検査する。
3. handoffの注入上限など、すでに実装と一致している説明を不要に変更しない。

## 非目標

- install/uninstallやhandoffのランタイム挙動の変更
- テストランナーの検出ロジックの変更
- 製品のランタイムへ新しい外部依存を追加すること（CI検査用ツールの導入は除く）
- 既存の警告を、根拠なく抑制すること

## 設計

### 1. ドキュメントとコメント

以下の誤認を、対応する実装の範囲に合わせて修正する。

- READMEのテストランナー説明は、構文エラー、テスト関数ゼロ、`source` 時のエラー、重複名、`test_` の綴り間違い、テストファイル不在など、波3で実装済みの静的ゲートを列挙する。同時に、これらのゲートだけでは各アサーションの意味やテストの十分性までは証明しないことを明記する。`CTS_NO_SKIP=1` はCIで強制する設定であり、ローカル実行時の既定値とは分けて説明する。
- READMEのバックアップ説明は、既存の `settings.local.json` をこのツールが初めて書き換える場合に、既存の `.cts-backup` が無ければ書き換え前の内容を退避する、という実際の条件に合わせる。今回新規作成する設定には「既存内容のバックアップ」は存在しないことを曖昧にしない。
- install.shとscripts/lib/common.shのリンク・移行コメントは、管理対象ディレクトリのコンテナシンボリックリンクを辿らず拒否する処理と、個別エントリの移行処理を混同しない表現にする。「すべてのリンク」や「常にリンク自体が移る」と読める断定を避ける。
- test/bash32-e2e.shのコンテナ説明を、`bash:3.2` の実行環境（Alpine/musl）に合わせる。
- test/test-uninstall.shの `chmod 444` ケースに、root実行では所有者権限の制約を受けず、モード保持の検証結果が通常ユーザー環境と異なり得ることを注記する。既存のinstall側の同種テストも、同じ誤認が残っていれば同じ基準で補足する。
- handoffの注入上限（1ファイル8KB、合計32KB、最大5ファイル）は現行実装・SKILL.mdと一致していることを確認し、差分が無い限り変更しない。

### 2. GitHub Actions

`.github/workflows/test.yml` の通常テストジョブに、次の検査を追加する。

1. Git管理下の `*.sh` を `git ls-files` で列挙し、各ファイルに対して個別に `bash -n` を実行する。複数ファイルを一度の `bash -n` に渡すと先頭ファイルしか検査されないため、ファイル単位のループにする。
2. Ubuntu runnerへShellCheckを導入し、同じファイル集合へShellCheckを実行する。導入方法とバージョンはCIログに残し、ShellCheckの非ゼロ終了をジョブ失敗として扱う。
3. テスト実行ステップを `CTS_NO_SKIP=1 bash test/run.sh` とし、環境依存でスキップされたテストをCIの成功に含めない。

bash 3.2の独立ジョブは、既存のDockerによる明示的な失敗条件を維持し、波4の一般的な構文・静的検査の対象変更によってその実行経路を置き換えない。

## 検証方針

- 変更前後で `bash test/run.sh` を実行し、既存テストが全件成功することを確認する。
- `bash -n` を全対象ファイルへ個別に実行する。
- CIと同じShellCheckコマンドを実行し、警告・エラーが残らないことを確認する。ローカルにShellCheckが無い場合は、CIで使用する導入手順を検証可能な環境で確認し、未検証の成功を主張しない。
- `git diff --check` を実行する。AGENTS.mdとCLAUDE.mdが存在する場合は `cmp -s AGENTS.md CLAUDE.md` も実行し、既存のプロジェクトルールと空白エラーを壊していないことを確認する。
- 独立したサブエージェントに、要件逸脱、過大なドキュメント主張、CIで実際には検査されない経路、ShellCheckの見落としを重点とする敵対的レビューを依頼する。

## 受け入れ条件

- README・コメントの記述が、現行コードの保証範囲を過大に主張しない。
- CIで `CTS_NO_SKIP=1`、ファイル単位の `bash -n`、ShellCheckが実行される。
- 既存テストが全件成功し、CI用の追加検査も成功する。
- 敵対的レビューで見つかった問題を修正・再検証し、ユーザーがマージできる1本のPRを作成する。エージェント自身はマージしない。
