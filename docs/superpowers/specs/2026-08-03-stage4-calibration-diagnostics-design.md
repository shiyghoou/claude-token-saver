# 段階4: キャリブレーションと診断 設計書

- 日付: 2026-08-03
- 対象Issue: #24
- 状態: 実装済み（#27）

## 1. 目的

段階3までのセッション切り提案は、移植元の実測から得た既定値を使っている。段階4では、対象プロジェクトの実際のトランスクリプトから閾値を算出し、トークン消費を押し上げている要因を診断する。

算出・診断は自動で行うが、設定の変更はユーザーが明示的に承認した場合に限る。既存の `token-report`、セッション切り提案、セッション引き継ぎとは独立した状態とし、互いの計測結果や状態を壊さない。

## 2. スコープと非スコープ

### スコープ

- セッション数と assistant ターン数によるキャリブレーション開始判定
- セッション単位の累積 `cache_read` の中央値による段階1単位の算出
- 現在値、推奨値、サンプル数、算出日、算出元の提示
- 実測診断と概算診断の分離表示
- 計測実行時およびセッション切り提案フック発火時の一度だけの促し
- 明示的な承認を表すコマンドによる `.claude/token-saver.json` の安全な更新
- 既存の段階3機能との共存、ドキュメント、回帰テスト

### 非スコープ

- MCP設定、Claude設定、スキル、常駐指示の自動変更
- 画像入力のトークン消費の計測
- 段階5の委譲判断ガイド
- `/clear` やセッション切りの自動実行

## 3. 採用するアプローチ

### 案A: 既存計測エンジンの拡張（採用）

`scripts/measure-token-usage.py` にセッション単位の集計、中央値、診断用のデータモデルを追加する。既存の重複排除、プロジェクト検出、MCP検出、サブエージェント集計を再利用し、`token-report` とキャリブレーションで同じ入力を使う。

読み取り専用のレポートと明示適用の処理は分離する。これにより、通常の計測を実行しただけで設定が変わることを防げる。

### 案B: キャリブレーション専用スクリプトを新設

専用スクリプトに分離する案は責務を明確にできる一方、トランスクリプト走査、重複排除、MCP・Agent判定が二重化し、既存レポートとの数値差が発生しやすい。共通ライブラリへ大きくリファクタリングする追加コストもあるため採用しない。

### 案C: Stopフックだけでキャリブレーション

Stopフックだけで判定すると、ユーザーが明示的に全期間の計測を確認できず、診断項目も限定される。またフックの実行環境に処理を集中させると、既存の fail-closed 契約を壊しやすい。採用しない。

## 4. 利用者向けの操作

### 4.1 読み取り専用のキャリブレーション・レポート

既存の導入先入口を拡張し、次の操作を提供する。

```text
./.token-saver/token-report.sh --calibrate
./.token-saver/token-report.sh --calibrate --days 30
```

通常の `token-report` と同じ期間・プロジェクト選択を使い、レポートへ以下を追加する。

- キャリブレーション判定（対象期間、セッション数、assistantターン数、必要数、判定結果）
- 現在の `initial_cache_read` / `increment_cache_read`
- 推奨する段階1単位と、その単位から導かれる段階2以降の閾値
- 中央値の算出根拠（サンプル数、算出日、算出元）
- 実測診断
- 概算診断
- 画像トークンが未計測であること

サンプル不足の場合は、推奨値を提示せず、不足している条件だけを表示する。通常のレポートは従来どおり読み取り専用とする。

`--calibrate` は、表示用Markdownに加えて `.token-saver/calibration/latest.json` を原子的に保存する。このファイルは適用候補の機械可読なスナップショットであり、ユーザー設定ではない。通常の `token-report.sh` も条件判定と一度だけの促し状態だけを更新するが、推奨値や診断の詳細は表示しない。

### 4.2 明示承認による適用

適用は専用の導入先入口から、ユーザーが `--apply` を付けた場合だけ行う。

```text
./.token-saver/token-calibrate.sh --apply
```

適用コマンドは `.token-saver/calibration/latest.json` の直前の有効なキャリブレーション結果を読み、現在値と推奨値を表示してから更新する。結果がない、サンプル不足、設定が不正、対象が変化している場合は更新しない。対象の変化は、選択条件、設定上の判定条件、入力トランスクリプトのパス・サイズ・更新時刻を含むスキャン識別情報で検出する。再計測後に適用する場合は、先に `--calibrate` を再実行する。

更新対象は `.claude/token-saver.json` の既存 `suggest_session_cut` 配下にある閾値だけとする。段階1単位を `initial_cache_read` と `increment_cache_read` に反映し、それ以外のキー、未知のキー、利用者設定は保持する。

キャリブレーション結果には、算出日、サンプル数、assistantターン数、対象期間、算出元、適用前後の値を記録する。これは履歴確認用のメタデータであり、次回の集計値や既存の設定値を上書きする根拠にはしない。

## 5. キャリブレーションの計算

### 5.1 判定条件

既定値は次のとおりとし、`.claude/token-saver.json` の root 直下 `calibration` で変更可能にする。

```json
{
  "calibration": {
    "min_sessions": 5,
    "min_assistant_turns": 100
  }
}
```

値は正の整数だけを受け付け、不正値や範囲外の値は既定値へ戻す。`--days` で選択した期間を判定対象とし、レポートには期間を明示する。

### 5.2 閾値

各メインセッションについて、重複排除後の assistant usage に含まれる `cache_read` を合計する。その値を昇順に並べ、中央値を段階1単位とする。サンプル数が偶数の場合は中央2値の整数平均を切り捨てる。外れ値1本が平均値を押し上げないことをテストで保証する。

`cache_read` の有効な正数サンプルがない、または中央値が0になる場合は、推奨値を算出しない。サンプル数とターン数の条件を満たしていても、根拠となる値がない場合は不足扱いとして促し・適用を行わない。

既存のセッション切り提案は「段階1単位を初期値とし、同じ単位を増分する」構造なので、推奨値 `B` は次のように扱う。

- 段階1: `B`
- 段階2: `B * 2`
- 段階3以降: `B * 3`, `B * 4`, ...

現在値と推奨値の単位、セッション数、assistantターン数、対象期間、算出元（セッション累積 `cache_read` の中央値）を同じレポート内に表示する。

## 6. 診断データ

診断は「実測」と「概算」を別セクションにする。概算値を実測合計へ加算しない。

### 6.1 実測として扱う項目

1. **閾値を大きく超えたセッション**
   - 推奨単位を基準に、少なくとも段階2相当を超えたセッションを抽出する。
   - 本数、累積 `cache_read`、期間内のメイン消費に占める割合を表示する。
   - Stopフックの発火記録がない場合は「切られなかった」と断定せず、トランスクリプト上の超過として表示する。

2. **メインへ積まれた重いツール結果**
   - メインの `tool_result` の発生箇所、ツール名、セッション、時刻、ペイロード量を収集する。
   - usageと安全に対応付けられる場合だけ実測トークンとして示し、対応付けられない場合はペイロード量を検出指標として明記する。

3. **未使用MCPサーバ**
   - 有効な設定として特定でき、メインおよびサブエージェントのトランスクリプトに対応する `mcp__<server>__` 呼び出しがない場合だけ未使用とする。
   - サーバ名の対応付けが曖昧なものや、無効化済み・検出不能なものは未使用と断定せず「判定不能」に分ける。

4. **サブエージェント利用**
   - 起動数、取得できる消費量、メイン消費との比率を既存のAgent集計から表示する。
   - `totalTokens` だけ取得できる場合と詳細usageがある場合を区別する。

5. **`/compact` の頻度と効果**
   - `/compact` の発生数を数える。
   - 直前のassistant usageから圧縮前の基準値を作り、直後のassistant usageと比較する。
   - 圧縮前の直近3ターンの中央値の90%以上へ戻った最初のassistantターンまでを回復ターン数とし、戻らない場合は未回復と表示する。

6. **画像**
   - 画像入力のトークン消費は未計測であることを明示する。

### 6.2 概算として扱う項目

- MCPサーバごとのツール定義サイズから見積もる常駐コスト
- 常駐指示ファイル・スキル一覧のサイズから見積もる比率

概算はUTF-8バイト数など再現可能な根拠と計算方法を併記する。実測合計、推奨値の算出、未使用判定の根拠には使用しない。

## 7. 一度だけの促し

### 7.1 状態

プロジェクトごとの `.token-saver/calibration/` 配下に、キャリブレーションの判定スナップショットと促し状態を保存する。設定ファイルとは分離し、次を記録する。

- 対象期間とサンプル条件
- 判定時点のセッション数・assistantターン数
- 促し済みかどうか
- 適用済み結果の識別情報

判定スナップショットは同じ条件での再実行では再促しせず、明示適用または新しいキャリブレーション周期が始まった場合だけ次の促しを許可する。レースを避けるため、状態更新は既存の状態ファイルと同じくロック、テンポラリファイル、renameで行う。

### 7.2 計測実行時

通常のレポートおよび `--calibrate` のレポート生成時に条件達成を確認する。未促しの場合、通常のレポートでは短い案内だけを、`--calibrate` では根拠と案内をレポート末尾へ一度だけ追加する。案内には適用コマンドを含めるが、コマンドを自動実行しない。

### 7.3 Stopフック発火時

Stopフックは既存のセッション切り提案を優先し、キャリブレーションのためにPythonや外部ネットワークを要求しない。現在のトランスクリプトから取得できる軽量なセッション集計をプロジェクト状態へ反映し、条件達成を確認できた場合だけ短い案内を出す。入力判定、状態更新、ロックに失敗した場合は、既存契約どおり無出力・標準エラー空・終了コード0で終了する。

完全な中央値・診断は `token-report.sh --calibrate` が行う。Stopフックの案内は「計測を実行して内容を確認し、承認する」という導線に限定し、設定ファイルを変更しない。

## 8. 設定更新の安全性

- `.claude/token-saver.json` が通常ファイルでない、symlinkである、JSONとして不正、rootがオブジェクトでない場合は更新しない。
- 更新前に対象キーを検証し、`suggest_session_cut` 以外を変更しない。
- 一時ファイルへ書き、同一ディレクトリ内のrenameで原子的に置き換える。
- 既存設定の未知キー、コメント相当の文字列値、キー順序以外の意味を保持するため、可能な範囲で構造化JSONを一度読み書きする。保持できない形式は安全側に倒して適用しない。
- 適用後に再読込・値検証を行い、失敗時は元ファイルを残す。
- MCP、Claude settings、スキル、フック登録自体は変更しない。

## 9. 実装の分割

Issue #24では、レビューとマージを分離できるよう、次の3波に分ける。

### Wave 1: 計測コアと読み取り専用レポート

- セッション別集計、中央値、判定条件、キャリブレーション結果モデル
- 実測・概算診断の収集とMarkdown出力
- `token-report.sh --calibrate`
- Python 3.6/3.8互換テストと既存token-report回帰テスト

### Wave 2: 明示適用と促し

- `token-calibrate.sh --apply` と導入先entrypoint
- 設定の安全な原子的更新、メタデータ、適用前後検証
- 計測時とStopフック発火時の一度だけの状態・案内
- symlink、競合、破損設定、既存設定保持のテスト

### Wave 3: 導線・文書・統合検証

- README、`skills/token-report/SKILL.md`、設計書、install/uninstall導線の更新
- 実測と概算の表示契約、未使用MCPの誤判定防止、段階3との共存テスト
- 全テスト、bash 3.2相当のE2E、独立した敵対的レビュー

各WaveはIssue #24の番号を含むブランチで実施し、個別PRとしてユーザーへマージを依頼する。エージェントはマージしない。

## 10. 受入条件との対応

| 受入条件 | 設計上の対応 |
|---|---|
| サンプル不足時は促さない | §5.1、§7 |
| 外れ値で中央値が引きずられない | §5.2、中央値の回帰テスト |
| 承認前にconfigを書き換えない | §4.2、§8 |
| unused MCPの誤判定なし | §6.1-3 |

## 11. 検討済みの制約

- 既存のtoken-reportの重複排除とMCP・Agent集計を唯一の基礎データとする。
- Stopフックの判定失敗は既存のセッション切り提案やユーザー操作を妨げない。
- Python 3.6/3.8を含む既存の互換性契約を維持する。
- ユーザー設定の変更は、明示的な適用操作以外では発生しない。
