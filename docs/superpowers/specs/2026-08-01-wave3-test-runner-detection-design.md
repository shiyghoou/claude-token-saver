# wave3 テストランナーの検出力強化の設計

## 背景

Issue #2 の波3では、テストが存在して件数だけを満たしていても、検証を実質的に失っていたり、アサーションの失敗がサブシェル内で飲み込まれたりする経路を塞ぐ。あわせて、root環境で権限テストがスキップされた事実、空の検索語を使ったアサーション、台帳に載っていないテストファイルをランナーの成功結果から隠さない。

波0〜2でテストランナー自身の隔離・アサーション層・実行件数・パス検査は強化された。しかし、次の変異は依然として緑になった。

- コメントに埋めた `assert_` や `assert_eq a a` だけを残したテスト関数
- アサーションを呼ぶ補助関数をコマンド置換・サブシェル・パイプ左辺から呼ぶテスト
- `_skip_if_root` が成功終了するため、未検証のテストが成功件数に混ざる経路
- `assert_contains` のneedleが空になったときの暗黙の全件一致
- heredoc内の記述や `.github/**` のパスリテラルを検査対象から外す経路
- 新しい `test/test-*.sh` を実行しても、台帳へ追加し忘れる経路

## 目的と非目的

目的は次の6点である。

1. 検証を含まないテスト関数を、コメントや自明なアサーションによって水増しできないようにする。
2. `_fail` の終了が内側のシェルだけに及ぶ危険な呼び出し位置を、直接呼び出しと補助関数経由の両方で検出する。
3. スキップを成功と混同せず、許容上限と「スキップ禁止」の実行モードを提供する。
4. 空needleによる `assert_contains` / `assert_not_contains` の無意味な成功を防ぐ。
5. パスリテラル検査の対象範囲とheredocの扱いを実際の検査意図に一致させる。
6. 実在するテストファイルと実行件数台帳を双方向に照合する。

非目的は次のとおりである。

- W3-7に列挙された波1・波2実装の回帰テスト追加。これは別Issueで行う。
- CIに `CTS_NO_SKIP=1` を設定すること、CIでの `bash -n` 導入、README全体の主張整理。これらは波4で行う。
- Bashの完全な構文解析器や新しい実行依存関係の導入。
- シェルの意味論を完全に証明すること。静的ゲートで保証できる範囲と限界は、検査コード内のコメントに明記する。

## 採用案

既存の依存ゼロのBash/AWK/grep構成を維持し、静的ゲートを保守可能な範囲で拡張する。各ゲートの変異耐性は `test/test-runner-selftest.sh` からランナーを複製して検証する。外部のShell Parser、Bats、Python実行時依存は追加しない。

### W3-1: 検証を含まないテストの判定

`_tests_without_assertion` は、テスト関数本文を判定する前にシェルコメントを除去する。引用符内の `#` とheredoc本文はシェルコメントとして扱わず、JSONや設定値に含まれる文字列を壊さない。既存のheredoc終端検出は維持する。

判定は「本文に `assert_` または `_fail` という文字列があるか」から、次の保守的な条件へ改める。

- `_fail` を実行経路として含むテストは検証ありとする。
- アサーション呼び出しを少なくとも1つ含み、呼び出し引数にシェル展開（`$var`、`${var}`、コマンド置換など）があるテストは検証ありとする。
- コメント中の名前、`assert_eq a a` だけのようなリテラル同士の自明な呼び出し、アサーション名を文字列として出力するだけの本文は検証なしとする。
- 固定値だけを検証することが本来の目的である例外は、テスト本文または直前行の `runner-allow` で明示する。

この規則は非自明性を構文上で近似するものであり、`assert_eq "$x" "$x"` のような意味上の同値性まで判定しない。その限界を検査コードのコメントに残し、READMEの「すべての空テストを意味論的に排除する」という表現は追加しない。

### W3-2: 飲み込まれるアサーションの補助関数経路

既存の直接呼び出し検査を残したまま、同じテストファイル内の補助関数を列挙する。`test_` で始まらない関数のうち、本文にアサーションまたは `_fail` を含む関数を「アサーション補助関数」として扱う。

次の位置で、その補助関数を呼び出している行を失敗にする。

- コマンド置換 `$()` の内部
- 明示的なサブシェル `( ... )` の内部
- パイプの左辺

関数定義の本文そのものにあるアサーションは通常どおり許可し、危険な位置での呼び出しだけを検査する。意図的に終了コードを捕捉するヘルパーは、既存仕様どおり同じ行または直前行の `runner-allow` で除外する。完全な関数間データフロー解析は行わず、1段の補助関数検出に範囲を限定する。

### W3-3: スキップの集計と実行モード

既存のroot権限テストが出力する安定したマーカー（`skip:`）をランナーが認識する。1つのテスト関数に複数のskip行があっても、スキップテストは1件として数える。

- テストの終了コードが0でもskipマーカーがあれば、成功件数へ加えずスキップ件数へ加える。
- 最終集計は `成功 N 件 / 失敗 M 件 / スキップ K 件` の形式で、スキップを隠さない。
- 実行件数台帳へ `skip-max N` 行を追加し、許容するスキップ数の上限を管理する。上限超過は失敗とする。
- `CTS_NO_SKIP=1` のときは、スキップが1件でもあれば失敗とする。スキップ件数自体は集計へ残す。
- `CTS_MIN_TESTS=0` は件数下限の無効化として既存どおり扱うが、`CTS_NO_SKIP=1` によるスキップ禁止は無効化しない。

実リポジトリの台帳には、現在の実行環境で確認した許容スキップ上限を設定する。CIでスキップを禁止する環境変数を設定する作業は波4に残す。

### W3-4: 空needleの防止

`assert_contains` と `assert_not_contains` は、`assert_count` と同じくneedleが空なら直ちに `_fail` する。エラーメッセージは呼び出し側の変数欠落を特定できる既存の日本語形式に揃える。

`_check_assert_layer` に、両関数の空needle呼び出しが失敗することを確認する素の終了コードプローブを追加する。これにより、アサーション層自身の改変で空needle guardが消えた場合も、通常のテストアサーションに依存せず停止できる。

### W3-5: パスリテラル検査の対象とheredoc

`_check_path_literals` の対象へ `.github/**` を加える。対象ファイルの除外はファイルパスの完全一致で維持し、`.github` 配下の実装ワークフローに新旧パスの重複定義が残れば報告する。

heredocの本文中にある `#` 行はシェルスクリプトの行頭コメントではないため、新パスリテラルの除外対象にしない。heredocの開始・終端を追跡し、本文中は通常の文字列として検査する。ただし、変数展開や文字列連結、`basename`・`dirname`・`printf`を組み合わせた動的なパス生成を正確に復元することは、この静的ゲートの保証範囲外とする。その限界を実装コメントに残し、契約テストで単一情報源との一致を引き続き守る。

### W3-6: 台帳の双方向照合

全件実行時に実際の `test/test-*.sh` を列挙し、台帳のファイル別キーと比較する。既存の「台帳にあるが実行されないファイル」の検査に加え、「実在するが台帳にないファイル」をエラーにする。新しいテストファイルを追加して台帳を更新し忘れた場合、テストを実行できても全体を失敗させる。

パターン実行時は対象ファイルだけの件数検査という既存の意味を維持し、全体の台帳差分検査は全件実行時に行う。`CTS_MIN_TESTS=0` を明示した場合だけ、台帳の件数・ファイル一覧の検査を無効化する。

## ファイル範囲

主な変更対象は次の3ファイルである。

- `test/run.sh`
- `test/lib/assert.sh`
- `test/test-runner-selftest.sh`

W3-3の許容スキップ上限を記録するため、必要に応じて `test/expected-min-count` の台帳行だけを更新する。W3-7対象の `test/test-handoff-*.sh`、`test/test-install.sh`、`test/test-uninstall.sh`、実装スクリプト、CI設定は変更しない。

## テスト方針

実装前に、現在のランナーで各変異が緑になることを確認できる自己テストを追加する。実装後は次を確認する。

- コメント中の `assert_` だけを残したテストが失敗する。
- `assert_eq a a` だけのテストが失敗し、展開を含む健全なテストは成功する。
- アサーション補助関数を `$()`、`( )`、パイプ左辺から呼ぶテストが失敗する。
- `runner-allow` 付きの終了コード捕捉ヘルパーは誤検知されない。
- root相当のskipマーカーが成功件数に混ざらず、集計と上限検査へ反映される。
- `CTS_NO_SKIP=1` でskipが失敗になる。
- `assert_contains` / `assert_not_contains` の空needleがアサーション層プローブで失敗する。
- heredoc本文のパスリテラルと `.github/**` の違反が検出される。
- 台帳にない実在テストファイルが検出され、`CTS_MIN_TESTS=0` では明示的に無効化できる。
- 既存の全テスト、`bash -n test/run.sh test/lib/assert.sh test/test-runner-selftest.sh`、`git diff --check` が成功する。

## 代替案と判断

Shell Parserを導入する案は、コメント・引用符・heredoc・関数呼び出しの解析精度を上げられるが、依存関係とCI環境を増やし、テストランナーの自己検査対象そのものを複雑化するため採用しない。

全テストを実行時トレースしてアサーションの実行を監視する案は、静的な危険記述の検出と相性が悪く、テストごとの環境差やトレース形式の依存を生むため採用しない。

既存の文字列検索をほぼ維持する案は変更量が少ないが、今回確認されたコメント・補助関数・heredoc・台帳外ファイルの変異を再び見逃すため採用しない。

この設計に従って波3の実装計画を作成し、W3-1〜6を順に実装する。
