# handoff区切りタグ属性の安全性再評価

作成日: 2026-08-03
対象Issue: #15
状態: 設計承認済み・仕様レビュー待ち

## 1. 目的

SessionStart フックが出力する区切りタグの `file=` / `path=` 属性について、
攻撃者が決められるファイル名・パスがコンテキスト、Markdown、ログ、シェル解釈へ
波及しない境界を明文化し、値の参照性を保ったまま安全な可逆エンコードへ移行する。

## 2. 現状と問題

現在の開始タグは次の形である。

```text
<handoff:ID file="..." path="...">
```

`file=` は pending ファイルの basename、`path=` は同ファイルまたはリンク先の
物理パスから作られる。これらは pending へ書き込める利用者・別プロセスが制御できる。
現在の `cts_sanitize_text` は制御文字、`"`、`<`、`>` を削除するが、その他の攻撃者由来
文字を残すため、値の意味を壊すうえ、危険文字の集合を将来漏らす余地がある。

動的な区切り ID によって本文からの終了タグ偽造は防げている。しかし、属性値そのものが
モデルのコンテキストへ入るため、次のリスクは残る。

- 攻撃者が決めた改行・制御文字・引用符・山括弧によるタグ行や Markdown の構造破壊
- `$()`、バッククォート、`;` などがログや補助処理でシェル断片に見えること
- 属性値をファイルパスとして読む利用者が、値を指示として誤解すること
- 一部の文字だけを削除するため、表示値と元のファイル名が一致せず復元できないこと

## 3. 脅威モデル

### 3.1 信頼領域

- フック本体とリポジトリに追跡されたスクリプト
- フックが実行時に生成するランダムな区切り ID
- 区切りの外側にある「フック自身の出力」と明示した固定文

区切り ID は実行ごとに変わり、pending の本文が事前に知ることはできない。

### 3.2 非信頼領域

- `.token-saver/handoff/pending/` に置かれたファイル名
- pending 内のシンボリックリンク名と、許可された範囲内のリンク解決先
- それらから算出される basename、表示パス
- 引き継ぎ本文そのもの

ファイル名には改行、空白、引用符、山括弧、制御文字、Unicode、シェル記号が含まれ得る。
Unix のパスには NUL を含められないため、NUL は入力集合の対象外とする。

### 3.3 想定する消費側

- Claude Code のコンテキストへ入る標準出力
- 人が読む Markdown とログ
- 開発者が属性を参照して `Read` などを行う補助的な操作

属性値をシェルへ渡して実行する契約は存在しない。実行されないことに依存するのではなく、
出力自体をシェル断片・タグ断片として解釈しにくい表現にする。

## 4. 採用方針

属性を削除せず、バイト単位のパーセントエンコードで保持する。これにより、通常のパスの
可読性と手動参照性を残しながら、値を元のバイト列へ戻せる。

### 4.1 エンコード規則

`file=` と `path=` の値は共通の `cts_encode_attribute` を通す。

- 入力は `LC_ALL=C` で1バイトずつ走査する
- 次の ASCII だけをそのまま残す: `A-Z a-z 0-9 . _ - /`
- それ以外の各バイトは大文字の `%XX` として出力する
- `%` 自身も `%25` になるため、エンコード済み文字列との曖昧さは生じない
- 改行、タブ、その他の制御文字、`"`、`<`、`>`、`&`、`\`、空白、Unicode、
  `;`、`$`、バッククォート、括弧はすべて直接出力しない
- `/` はパスの区切りとして残す。Windows 形式の `\` やドライブ記号の `:` はエンコードする

例:

```text
normal-name.md              -> normal-name.md
日本語.md                   -> %E6%97%A5%E6%9C%AC%E8%AA%9E.md
a"b<c>.md                  -> a%22b%3Cb%3E.md
a b$(touch X).md           -> a%20b%24%28touch%20X%29.md
a<LF>b.md                  -> a%3C%0Ab%3E.md（`<LF>` は0x0Aの改行）
```

UTF-8文字は表示上の文字ではなく、元のUTF-8バイト列を順に `%XX` 化する。エンコードは
正規形を1つだけ持ち、同じ入力は常に同じ表現になる。

### 4.2 出力境界

- 開始タグの構造と動的な区切り ID は維持する
- `file=` / `path=` の値だけをエンコードし、属性名やタグ自体は変更しない
- 属性は引き続き区切りの内側に置く
- 区切りの外側の固定文には、攻撃者由来のファイル名・パスを絶対に含めない
- 読み取り失敗・切り詰め・移動失敗などの注記は、エンコード済み属性を参照させる既存方針を維持する
- エンコード処理に予期せず失敗した場合も、raw 値をフォールバック出力しない。空属性または
  既存の安全な失敗経路へ倒し、標準エラーを汚さない

### 4.3 実装境界

`scripts/lib/common.sh` にエンコード関数を置き、`scripts/handoff-check.sh` の `_open_tag`
からだけ呼び出す。フック実行時に Python、jq、外部 URL デコーダーへ依存しない。

現行の削除型 `cts_sanitize_text` は属性出力のためには使用しない。名前が示す「一部を
削除して安全化する」意味を残すと、別の出力箇所が誤用するため、属性専用の関数名と契約へ
置き換える。

実装は Bash 3.2 で利用できる構文に限定する。`${var,,}`、連想配列、無防備な空配列展開、
Bash 4以降の機能は使わない。バイトの16進化には既存の最小依存方針に合うコマンドだけを
使い、入力の各バイトを失うコマンド置換を作らない。

## 5. テスト方針

既存の fence 検査ヘルパーを使い、実際のフック出力を対象にする。

### 5.1 属性エンコード

- 通常の ASCII パスは安全文字がそのまま残る
- 空白、改行、タブ、制御文字、DEL、`"`、`<`、`>`、`&`、`\`、`%`、`;`、`$`、
  バッククォート、括弧が `%XX` になる
- 日本語などのUnicodeをUTF-8バイト列として可逆に表現する
- `file=` と `path=` の両方が同じエンコード規則を使う
- エンコード後の開始タグが1行であり、未エンコードの攻撃者文字列がタグ構造へ現れない
- 代表ケースを既知の `%XX` 期待値と照合し、異なる入力が同じエンコードへ潰れないことを確認する

### 5.2 コンテキスト・ログ・シェル境界

- 攻撃者文字列に「指示を撤回する」等の行、Markdown記号、シェル断片を含めても、区切りの外側へ出ない
- `$()`、バッククォート、リダイレクト、セミコロンを含む名前で外部ファイルが作られない
- `file=` / `path=` の属性を閉じる引用符や山括弧を含む名前でも、開始タグの解析が壊れない
- 既存の秘密情報非漏えい、本文偽造防止、終了コード0、標準エラー空の契約を維持する

### 5.3 互換性

- 既存の安全なファイル名・パスで、claim、読み取り、consumed 移動が変わらない
- Bash 3.2 のDocker E2Eを通過する
- 全体テストと既存の静的ゲートを通過する

## 9. 代替案と不採用理由

### 属性を削除する

タグ偽造面は最小になるが、読み取り失敗や移動失敗の対象を人が特定できず、既存の手動復旧
ワークフローを壊すため不採用とする。

### Base64urlで属性全体を包む

安全な文字集合を作りやすいが、通常のパスも完全に不透明になり、手動参照のコストが高い。
可逆性は満たすが、Issueの目的である参照性とのバランスが悪いため不採用とする。

### XML/HTMLエンティティだけで逃がす

引用符や山括弧は扱えるが、制御文字・Unicode・Markdown・シェル記号との境界を別途定義する
必要があり、消費側がエンティティを解釈する前提も増える。バイト単位の単一規則にできる
パーセントエンコードを採用する。
