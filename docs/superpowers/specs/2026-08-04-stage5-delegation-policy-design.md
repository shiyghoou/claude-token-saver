# 段階5: 委譲判断ガイドと移植元の切り替え 設計

## 1. 目的

Claude Code が、メイン会話へ重い作業を積み続ける前に「委譲するか」「どの能力帯へ渡すか」を判断できる、必要時だけ読み込む `delegation-policy` スキルを追加する。

段階5の完了時点では本リポジトリを委譲方針の正とし、非公開の移植元は本リポジトリを導入する側へ切り替えられる。ただし本Issueでは移植元リポジトリを変更せず、安全な切り替え手順だけを文書化する。

## 2. 前提と境界

- 段階1〜4は `main` に実装済みである。
- 段階4のキャリブレーションと診断は、委譲判断の参考情報になり得るが、段階5から snapshot のJSON構造へ依存しない。
- `install.sh` / `uninstall.sh` は `skills/*/` を一般化して発見し、リンク、コピー、台帳、`.gitignore`、同名保護を処理済みである。
- 委譲判断はエージェントが明示的にスキルを読み込んだときだけ行う。常駐指示、Stopフック、自動実行は追加しない。
- 既存の公開CLI、環境変数、設定JSON、台帳schema、フック出力は変更しない。

## 3. スコープ

### 含むもの

1. `skills/delegation-policy/SKILL.md` の追加
2. 委譲判断の順序、非コスト理由、結果回収、能力帯選択、数値の限界の明文化
3. 既存の一般化された installer / uninstaller で新スキルを安全に往復できることの回帰テスト
4. README と基礎設計書の実装済み表示、使い方、移植元切り替え手順の更新

### 含まないもの

- 非公開の移植元リポジトリ、実測レポート、個人設定の変更
- 委譲の自動発火、エージェントの自動生成、設定ファイルの自動変更
- 特定ベンダーのモデル名、価格、固定トークン閾値を普遍的な規則として埋め込むこと
- Claude Code plugin / marketplace 形式への変更
- 既存スキルの内容変更

## 4. スキルの責務

### 4.1 読み込み条件

frontmatter の `description` は、重い調査・実装・レビューを委譲するか、並列化するか、能力帯を選ぶ必要がある場面を対象にする。小さな作業へ常に委譲させる表現は避ける。

### 4.2 判断順序

判断は次の順序に固定する。

1. **非コスト理由を先に確認する。** 並列化、ツール制限、専門知識の分離、独立した敵対的レビューが必要なら、トークン節約だけで却下しない。
2. **作業の重さを確認する。** 調査結果やツール出力がメイン会話へ相応に積み上がる作業だけを委譲候補にする。
3. **残りの会話期間を確認する。** 今後も同じ会話が続くほど、メイン文脈を軽く保つ価値が高い。直後に会話を切ることが確定しているなら、節約だけを目的に委譲しない。
4. **起動と統合の固定費を確認する。** 指示の受け渡し、サブエージェントの起動、結果の読解・統合が、直接実行より重くならないかを見る。
5. **能力帯と境界を選ぶ。** 創作、設計、矛盾発見、敵対的レビューには高い能力を、機械的な検索、形式確認、限定されたテスト実行には軽量な能力を選ぶ。
6. **回収計画を決めてから起動する。** 完了条件、返してほしい証拠、共有状態の所有範囲を明示し、起動した結果を必ず回収してメイン側で統合する。

### 4.3 委譲しない代表例

- 1〜2回の短い読み取りや、メイン側ですでに十分な文脈を持つ小変更
- 強く逐次依存し、結果ごとに次の操作を変える必要がある作業
- 同じファイルや外部状態を競合して変更する作業
- 回収・検証のコストが直接実行を上回る作業
- 次のターンでセッションを切ることが確定しており、非コスト理由も無い作業

## 5. 段階4との整合

`token-report` / `--calibrate` の診断から、メイン側の重い tool result、Agent 利用、会話継続による負荷を人が読み取り、委譲方針を見直してよい。一方で `delegation-policy` は次を行わない。

- `.token-saver/calibration/latest.json` を解析しない
- キャリブレーションの fingerprint や内部キーを公開APIとして扱わない
- 計測値だけから委譲やモデルを自動決定しない
- `.claude/token-saver.json`、フック、MCP、エージェント設定を変更しない

これにより段階4のschema変更が段階5を壊さず、段階5も段階4の安全な明示適用契約を侵さない。

## 6. 数値とモデル表現

移植元の数値は単一リポジトリ・限られた期間・当時のモデル/MCP/指示構成に依存する。サブエージェント起動の固定コストも直接測定していないため、本スキルは固定の損益分岐点を提示しない。

モデル名ではなく「高能力」「軽量」という役割で記述する。利用可能なモデル、価格、速度、ツール権限が変わった場合も、同じ判断原則を使えるようにする。

## 7. 導入・取り外し

新スキルのために `install.sh` / `uninstall.sh` の実装分岐は追加しない。既存の `skills/*/` 発見を単一情報源とし、次を実スキル名で回帰テストする。

- 通常時は `.claude/skills/delegation-policy` へリンクし、台帳と `.gitignore` に記録する
- `CTS_NO_SYMLINK=1` では所有マーカー付きコピーを配置する
- 導入先に同名の利用者所有スキルがある場合は上書きも台帳登録もしない
- uninstall は台帳どおりのリンク/コピーだけを外す
- install → uninstall → install の往復で再導入できる

## 8. 移植元の切り替え手順

README に、移植元側で別途行う手順を記載する。

1. 移植元の運用規約に従い、独立したIssue/branchを作る。
2. 本リポジトリの `install.sh` を移植元へ実行し、`delegation-policy` を含むスキル、フック、台帳を検証する。
3. 移植元固有の実測値・秘密情報は移さず、必要ならローカル文書として保持する。
4. 新スキルを実際に読み込み、旧方針と判断原則が一致することを確認する。
5. その確認後にだけ、移植元の重複する方針文書やスクリプト実体を移植元側のPRで削除する。
6. uninstall 往復と既存運用を検証し、本リポジトリを正とする。

段階5のPRはこの手順を提供するところで止め、移植元への書き込み権限を暗黙に拡張しない。

## 9. 検証

- 新しいスキル契約テスト
- `test-install.sh` / `test-uninstall.sh` の実名回帰
- README / 基礎設計書の文書契約テスト
- `CTS_NO_SKIP=1 bash test/run.sh`
- `bash test/test-python-compatibility.sh`
- `bash test/bash32-e2e.sh`
- `git diff --check`
- 実装者とは別の fresh Sol レビュー

## 10. 受入条件との対応

| 受入条件 | 対応 |
| --- | --- |
| 段階4と不整合がない | §5で疎結合と非自動変更を固定する |
| 全予定機能が動く | スキル本体、導入往復、README、基礎設計、移植手順を一つのPRで揃える |
| 既存テストが通る | §9の対象・全件・互換性・Bash 3.2検証を実行する |
| 公開APIを壊さない | 既存CLI/設定/schema/フックを変更せず、新規スキル追加だけにする |
